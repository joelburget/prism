# Query engine with NULL support — Typescript

Node.js 25+ executes the erasable TypeScript directly. For static validation, run `npm ci --ignore-scripts` then `npm run typecheck` (TypeScript 5.9.3, strict mode). `npm test` runs `tests.ts`, a white-box suite over the optimizer.

Run `./run.sh`. It reads one protocol-v1 `query-null` JSON request from stdin and writes one JSON response. Every request starts a fresh process. Domain errors exit zero and contain only the fixed error code. No SQL library or external query engine is used.

The modules separate wire validation and models, SQL tokenization/parsing, binding and type checking, execution/optimization, incremental view maintenance (`views.ts`), and the base tables and command protocol (`store.ts`). Binding resolves columns to flattened row slots and verifies all expressions before evaluating rows, including unreachable expressions and empty tables. The logical plan carries typed expressions, input tables, scan predicates, join kinds, and ordering.

SQL NULL is JavaScript `null` in every value position, so UNKNOWN is simply a `null` predicate result. Predicates are applied through a single `holds` helper that keeps only TRUE, which is what makes FALSE and UNKNOWN behave identically in ON, WHERE, and HAVING. AND and OR absorb UNKNOWN before their operands are inspected; every other scalar operator propagates it. Aggregates skip NULL inputs and return NULL when nothing is left, while COUNT stays non-null. An outer join pads unmatched left rows with NULL for the whole right side, regardless of declared nullability.

The binder computes a conservative `nullable` flag for each expression, marking the padded side of every outer join nullable even when its columns are declared `NOT NULL`. An untyped NULL literal carries no type and unifies with whatever its context requires, without weakening type checking elsewhere.

Optimization performs bottom-up folding of constant scalar expressions, including NULL-valued ones, and pushes single-source WHERE conjuncts into join input scans. Conjuncts referencing multiple sources remain above the join. Three rules depend on the nullability flags: `x = x` and `p OR NOT p` fold only over non-nullable operands; a conjunct is never pushed below an outer join into its padded input; and a WHERE conjunct that rejects an all-NULL row provably discards every padded row, so it converts that outer join into an inner join and then becomes eligible for pushdown. Stable nested-loop joins, encounter-ordered groups, first-occurrence DISTINCT, stable sorting with explicit NULL placement, and pagination preserve the documented ordering in either mode.

An input with `commands` instead of `queries` selects the view protocol, which reuses that same parser, binder, optimizer and expression semantics. A base row carries a private identifier and a stable encounter position; an update keeps its position, an insertion appends, and identifiers are never reused. `create` runs one full query and keeps the state that produced it; afterwards every batch is turned into a delta and pushed through the maintained stages — per-source scans, one state per join, the WHERE survivors, and either projected rows or aggregate groups. Views whose tables are untouched are skipped entirely, and only ORDER BY, OFFSET and LIMIT are resolved at read time over the maintained result.

Each join keeps its left tuples and its right scan rows in hash indexes built from the equality conjuncts of the ON condition, so a change visits candidate partners instead of the opposite relation; a NULL key is stored in a bucket that is never probed, because NULL never matches NULL. A left tuple owns its matches and, while it has none, the NULL-extended stand-in an outer join must publish, so losing a last match or gaining a first one is a local edit. Duplicate contributions are distinct tuples, so DISTINCT buckets and aggregate groups survive until their last member leaves. Aggregates keep per-group running state; deleting the current MIN/MAX or the first-encountered member revisits that one group. Encounter order is carried as the vector of source positions, which decides ORDER BY ties, DISTINCT first occurrence and group order.

`apply` stages a whole batch in a private overlay, so a rejected change leaves base rows, reserved identifiers, view state and the revision untouched; a committed batch updates rows, identifiers and every view together, and a row changed on both sides of a join is neither lost nor counted twice.

Supported: SELECT/WHERE, inner and LEFT [OUTER] joins, nullable schemas, NULL/IS [NOT] NULL/COALESCE, grouped and global COUNT/SUM/MIN/MAX, GROUP BY/HAVING, DISTINCT/ORDER BY with NULLS FIRST|LAST/LIMIT/OFFSET, and incrementally maintained views over that whole subset in either optimizer mode.

Validation: all 55 public baseline and 20 public extension cases pass. `npm test` additionally replays command scripts against every maintained view and compares each read with a fresh query over the same live rows, in both optimizer modes. This directory is self-contained; `starter.json` lists its export files. Build outputs and dependency installations are ignored.
